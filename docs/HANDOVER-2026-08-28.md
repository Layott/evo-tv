# Handover, 28 August 2026

## The EVO TV filler never played, and it was not a config problem

Owner reported the channel's own advert not playing when the channel is off
air. It had been "fixed" on 19 and 20 August, so the first job was working out
what was still wrong.

Everything the server controls was already correct, which is why this survived
the earlier passes:

- `/api/channel/breaks` returns `fillerOnDrop: true`, `adFree: false`
- `/api/ads/serve?placement=live_filler` returns the row, active, 18 impressions
- the file is public on Spaces, HTTP 200, `video/mp4`
- `FillerScreen` mounts and hands the URL to a `<video>`

Read off prod in Chrome, nineteen seconds after mount:

```
readyState: 0     HAVE_NOTHING, not one frame decoded
networkState: 2   still downloading
videoWidth: 0
buffered: []
error: null       nothing fires, so no fallback runs
```

**Cause: the creative is not faststart.** Atom order in the file:

```
ftyp -> free -> mdat (77,996,155 bytes) -> moov
```

`moov` is the index, and a browser decodes nothing without it. Written that way
the player has to pull all 78 MB before frame one. It raises no error while it
does, so `onError` never fired and the fallback never came back. The viewer got
a black rectangle labelled "Back shortly".

The file was also far heavier than anything a viewer could play: **2560x1440 at
120 fps, 33.9 Mbps, for an 18 second loop**. That is four times the entire
four-rung ladder budget. Even written correctly it would have stalled a phone.

### Why every earlier fix missed it

The 19 and 20 August work fixed four real causes (mounted on one page only,
gated behind the breaks master switch, a row saved with an empty `mediaUrl`, a
dead feed). All four were about whether the filler was *reached*. None of them
asked whether the picture actually moved once it was, and the file itself was
never examined.

This is the same lesson already in memory as `feedback_verify_behaviour_not_sha`
and in the 19 August handover: **ask whether the picture is moving.** Here even
that was not enough on its own, because playback never began at all, so there
was no `currentTime` to watch.

## What was built

Branch `fix/filler-faststart-and-watchdog` off `dev`.

**1. The creative, re-encoded.** 1080p30, CRF 26 capped at 3 Mbps, faststart.

```
78,034,881 bytes -> 7,388,768 bytes    (10.6x smaller)
33.9 Mbps        -> 3.2 Mbps
2560x1440@120    -> 1920x1080@30
moov at the end  -> moov at byte 36
```

**2. `lib/media/mp4-faststart.ts`,** a box walk that reads the head of an mp4
and says `faststart`, `index-at-end`, or `unknown`. It answers from `mdat`
arriving first, so a one megabyte slice of an eighty megabyte file is enough.
`unknown` means allow: refusing a good upload on a guess is worse than
accepting a slow one. 8 unit tests.

**3. The guard, in `components/admin/media-upload.tsx`,** so this cannot recur.
An index-at-end mp4 is refused before the upload starts, naming the fix
(`-movflags +faststart`). A video over 6 Mbps average gets a warning but is
allowed, because only the operator knows whether a heavy sting is deliberate.

Browser side rather than server side on purpose: the backend image carries no
ffmpeg (`workers/transcode.ts` degrades when it is absent, by design), the
droplet has two cores already serving the channel, and the person who can
re-export the file is standing in front of the form.

**4. `lib/media/playback-health.ts` + `components/stream/use-first-frame-watchdog.ts`,**
wired into both `FillerScreen` and the mid-roll in `ChannelBreaks`. If no frame
is decoded within 8 seconds, the layer gives the screen back: filler falls back
to the poster and the off-air text, a mid-roll ends and returns to live. 7 unit
tests on the predicate, including the exact state read off prod.

This is the part that matters beyond this one file. `adMaxSec` would eventually
lift a stuck mid-roll, but filler loops and had no such stop, which is how off
air stayed black indefinitely rather than merely for a while.

### The watchdog, proved end to end

Run locally against a server that reproduces the fault exactly: the real first
two megabytes of the broken file, then a trickle, so the container opens
validly and the index never arrives. Measured across a client-side navigation
so the clock starts at the actual mount rather than at whenever the probe
attached:

```
ms     0   filler-mounted        readyState 0, src .../stalls.mp4
           (no error event, ever)
ms  8883   filler-removed        screen: poster + Off air
```

Against an 8,000 ms deadline. **No `error` event fired at any point**, so
nothing but the watchdog could have taken the layer down. That is the whole
point of the change.

Two false starts worth recording, because both would mislead somebody
repeating this:

- **Serving zero bytes does not reproduce it.** Chrome cannot open the
  container, fires `error` immediately, and the old code recovers by itself.
  The bytes have to be a real `ftyp` plus real `mdat`.
- **The broken file loads instantly on this machine now**, because 78 MB of it
  sits in Chrome's cache from the prod visit that diagnosed it
  (`cache-control: max-age=3600`). A cached probe proves nothing.

### The fixed creative, proved end to end

```
ms     0   filler-mounted
ms    47   loadeddata            readyState 4, videoWidth 1920
```

Playing, and the picture moves: two screenshots four seconds apart show
different frames of the advert. Checked at 1425 wide and at a real 390x844 in a
same-origin iframe (`resize_window` lies on a maximized window). No horizontal
scroll on mobile, hero intact.

**A trap that cost time here:** Chrome does not advance video in a hidden tab,
and the extension's tab is hidden between calls. `currentTime` sat at 0.06 and
`paused` stayed true while the element was demonstrably healthy at
`readyState 4`. `play()` resolves without error and still does not advance.
Comparing two screenshots is the way to prove motion; reading `currentTime`
from a background tab is not.

## Shipped to prod, and what the deploy walk found

Merged `fix/filler-faststart-and-watchdog` -> `dev` (#259) -> `staging` (#260)
-> `main` (#261), `50d7e3f`. Bundle on prod swapped 540 seconds after the merge.

**Proved by behaviour, not by a SHA.** A deliberately broken 44 KB mp4 (`ftyp`
at 4, `mdat` at 44, `moov` at 40,296) was picked in the real admin Ads form on
prod. The guard refused it before anything reached the bucket, and the
`live_filler` row was untouched.

That walk also found a bug in what had just shipped. The refusal said:

> nothing appears until all **0 MB** has downloaded

`formatMb` rounded to whole megabytes, so any file under half a megabyte read
as zero. A size that reads as a bug undercuts the warning carrying it. Fixed on
`fix/file-size-reads-zero-mb`: `lib/media/file-size.ts` picks the unit from the
file, never rounds a real file to zero, keeps one decimal between 1 and 10 MB,
and is unit tested. The message now reads "a viewer sees nothing until the
whole file (44 KB) has downloaded", which is true at any size.

Worth noting the guard was only exercised because the test file was small
enough to hand to the browser: the 10 MB upload cap meant the original 78 MB
creative could not be used as the probe.

### The second deploy, and why the bundle check was useless for it

`fix/file-size-reads-zero-mb` went `dev` (#262) -> `staging` (#263) -> `main`
(#264), `e9e75da`.

**The bundle fingerprint on `/home` never changed, and that was correct.** This
fix only touches `media-upload.tsx` and adds `lib/media/file-size.ts`, neither
of which `/home` loads, so watching the home page's chunk list for a change
would have waited for ever. It reported "no change after 20 min" and meant
nothing.

Proved by behaviour instead, which is the rule anyway. The same 44 KB file,
picked in the prod admin Ads form:

> This MP4 keeps its index at the end, so a viewer sees nothing until the whole
> file (**44 KB**) has downloaded. Re-export it with faststart (ffmpeg:
> -movflags +faststart) and upload it again.

Sheet cancelled, nothing saved, `live_filler` still on
`evo-tv-filler-411f77868de5b691.mp4`.

**The lesson generalises:** a deploy detector built on one page's assets only
sees changes that reach that page. Ask the changed surface to behave.

## Next, agreed with the owner: squeeze-back ad breaks

The show shrinks to a muted corner tile while the advert plays full size
underneath with sound. Owner's picture is in the session; the shape is the
broadcast squeeze-back.

**Decisions taken:**

- **Website and app**, not website only.
- **An operator setting per channel**, not a replacement for the current
  full-screen break.
- **Parity on the app**, recommended and accepted. The reasoning: the app is
  where the viewers are, it is a sellable inventory format or it is nothing,
  and the downside is bounded because the fallback is the full-screen break
  that already exists and is tested.

**What was checked rather than assumed:**

- The app uses `expo-video` (`useVideoPlayer` + `VideoView`, SDK 52). Two
  separate players each with their own view is a supported shape and `muted` is
  a per-player property, so **no native module is needed**. My initial worry
  about that was misplaced.
- **Two `VideoView`s cannot share one player.** Attaching a player to a second
  view detaches it from the first, which would silently kill the live picture.
  The corner tile and the full-size ad must be two distinct players, never one
  player rendered twice. This is the landmine to write into the spec.
- The real risk is Android concurrent hardware decoder limits on cheap phones.
  Failure mode is "this device gets the old full-screen break", not a black
  screen.

**Open design question for the spec:** at 390px wide a corner tile at desktop
proportions is about 97px across, too small to follow a match. The tile likely
wants to be proportionally larger on a phone than on a monitor.

The website half is bounded: the live `<video>` never changes source, a
transform on the wrapper moves it into the corner. The app half is a new
subsystem (`channel-overlay-host.tsx` carries a comment saying ad breaks were
deliberately left out), so the work is architectural: spec, then plan, then
code. **Nothing has been written yet.**
