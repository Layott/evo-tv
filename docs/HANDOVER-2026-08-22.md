## Where sign-ins and app viewers actually are

**The finding that started it.** `/api/edge/whereami` (shipped yesterday as
`36f77dd`) answered, on production:

```
"verdict": "No Cloudflare headers at all: this request did not come through the proxy."
```

DNS explains it:

| host | resolves to | proxied |
|---|---|---|
| `evotv.co` | 104.21.29.7, 172.67.171.57 | yes: `Server: cloudflare`, `CF-RAY` |
| `api.evotv.co` | 138.68.126.199 (the droplet) | **no**: only `Via: 1.1 Caddy` |

Sign-in posts to `BETTER_AUTH_URL`, which is `https://api.evotv.co`. So the
managed transform the owner switched on yesterday cannot reach it, and neither
can the header fix from 21 August: **there are no headers on that request to
read.** The app talks to the same hostname, which is also why every app viewer
sat in the audience breakdown with no country next to a website viewer showing
`NG`.

Note this contradicts the note in
[[project_post_launch_cleanup_2026_08_12]] that says "only `api.` is proxied".
The evidence above is the other way round. Trust the evidence.

### What shipped: PR #247, `feature/geoip-on-the-droplet`

`lib/geo/ip-location.ts` asks three sources in order of what each costs:

1. **Cloudflare headers** when the request came through the proxy. Free.
2. **A local city database**, no network, no third party. Covers what
   Cloudflare never saw, which on `api.` is everything.
3. **IPinfo**, one HTTPS call, only for addresses the local file places in a
   country but not a city.

Cached a day per address, so a viewer heartbeating every fifteen seconds costs
one lookup a day rather than 5,760. Every step is optional: with no file and no
token it returns null and callers degrade to exactly the old behaviour. It
**never throws**, because no location is an acceptable outcome inside a sign-in
and an exception is not.

Wired into `recordLoginEvent` and the viewer heartbeat. `/api/edge/whereami`
now reports all three sources rather than only Cloudflare.
