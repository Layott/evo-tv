### What shipped: PR #247, `feature/geoip-on-the-droplet`

`lib/geo/ip-location.ts` asks three sources in order of what each costs:

1. **Cloudflare headers** when the request came through the proxy. Free.
2. **A local city database**, no network, no third party. Covers what
   Cloudflare never saw, which on `api.` is everything.
3. **IPinfo**, one HTTPS call, only for addresses the local file places in a
   country but not a city.

Cached a day per address, so a viewer heartbeating every fifteen seconds costs
one lookup a day rather than 5,760. Every step is optional: with no file and no
token it returns null and callers degrade to exactly the old behaviour. It
**never throws**, because no location is an acceptable outcome inside a sign-in
and an exception is not.

Wired into `recordLoginEvent` and the viewer heartbeat. `/api/edge/whereami`
now reports all three sources rather than only Cloudflare.

## Which database, settled by measuring

I told the owner GeoLite2 was "generally sharper on mobile networks". Then the
owner made a MaxMind account and I measured both against 17 real addresses,
mostly Nigerian mobile ranges. **That claim did not hold.**

| | DB-IP City Lite | MaxMind GeoLite2 |
|---|---|---|
| named a city | **17 of 17** | 10 of 17 |
| `105.112.0.1` Airtel NG | Ikenne, Ogun State | NG only |
| `41.190.3.1` NG broadband | Lekki, Lagos | NG only |
| `8.8.8.8` | Mountain View, California | US only |
| `1.1.1.1` | Sydney, New South Wales | nothing |

GeoLite2 abstains where it is unsure, which is a defensible design. But here
**every abstention becomes an IPinfo call**, and IPinfo has a monthly allowance
where a local file has none. DB-IP stays the default.

DB-IP errs the other way: it labels ranges down to a neighbourhood, mobile
ranges included, e.g. "Lagos (Victoria Island Annex)", "Lekki (Banana Island)".
**A handset is wherever the carrier's gateway is not**, so that district is a
precision the data does not have, and an operator reading it in the audit log
would believe it. `trimLocality` stores the city and drops the parenthetical.

Coverage is not accuracy, and this sample cannot prove accuracy without ground
truth. What it does prove is that the assumption behind the recommendation was
wrong, which is why the file on the droplet did not change.

**The MaxMind key exists and is unused.** Setting `MAXMIND_LICENSE_KEY` in
`/srv/evotv/.env` switches `geoip-refresh.sh` to GeoLite2 on the next run. It
is deliberately not set. Account 1397953.

## IPinfo

Token is **installed** at `/srv/evotv/.env` line 88, file still `600 root`.
Proved from the droplet itself: `41.58.0.1` returns Lagos, Lagos, NG.

The dashboard shows the plan as **Lite**, and IPinfo's Lite *endpoint*
(`api.ipinfo.io/lite/{ip}`) is country and ASN only. The classic endpoint the
module actually calls, `ipinfo.io/{ip}/json?token=`, **does return city** on
this token. Checked both before wiring anything.

Takes effect when the containers restart, which the deploy does anyway.

## Bounding the IPinfo spend

The owner proposed calling IPinfo only on each user's **first and last sign-in
per day**. Right concern, unworkable rule: **which sign-in was the last is not
knowable when the row is written**, so it needs a nightly pass to fill rows in
afterwards. Two changes instead, both tighter:

- **`remote` is opt-in and only the sign-in path passes it.** Heartbeats are
  the volume, tens of thousands a day against a handful of sign-ins, and they
  store the country alone, which the local file gives for effectively every
  address. So heartbeats never call out, and **every** sign-in is still located
  rather than one or two per person per day.
- **A daily ceiling counted in Valkey**, `IPINFO_DAILY_MAX`, default 1,000.
  Shared, because two api containers each holding their own would permit twice
  the number. Over the line it logs once and uses the local file.

Expected steady-state IPinfo volume: near zero, since DB-IP named a city for
17 of 17 sampled addresses and only a miss triggers a call.

**A trap worth writing down: the droplet's git HEAD moving does not mean the
deploy has finished.** `autodeploy.sh` pulls, and only then runs `deploy.sh`,
which builds the image before it recreates anything. Checking a minute after
HEAD moved showed no volume mount and no `IPINFO_TOKEN` in the container, and
both looked like the deploy had silently skipped them. They were simply the old
containers, created at 00:12, while `pnpm build` was still running. **Verify
against behaviour, not against HEAD.** This is the second time this repo has
produced that exact false alarm; see [[project_admin_walk_and_app_parity]].

The api containers are recreated with `docker compose up -d --force-recreate`
per service (`deploy.sh:107`), which reads the compose file synced earlier in
the same run, so the new volume and the new `.env` both land in this deploy.
`COMPOSE_CHANGED` only recreating caddy is fine for that reason.
