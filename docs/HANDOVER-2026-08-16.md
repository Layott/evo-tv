## Browser push works, and is proven

The server could send a Web Push since the notifications work landed, and
production has had a VAPID pair configured all along. Nothing ever called
`navigator.serviceWorker.register`, so **no browser was ever subscribed and
every send counted zero deliveries.**

`hooks/use-web-push.ts` closes that. The notification settings card, which was
four switches in React state and a save button that slept for half a second and
said "saved", now reads and writes `/api/users/me/prefs`, which has carried a
`notifOptIn` field of exactly those four keys the whole time.

The reminder cron sent to the app only, so a reminder set on the website
reached nobody. It writes the durable notification row and sends on both
transports now, and respects the event-reminder preference: an opt-out is
skipped but still stamped, so opting back in does not bury someone in
reminders for programmes that already aired.

Verified in real Chrome against a real FCM endpoint, not a mock:

| Check | Result |
|---|---|
| Subscribe from the settings switch | endpoint on `fcm.googleapis.com` |
| Survives a browser restart | switch reads back on |
| Announcement to that account | `webDelivered: 1`, shown by the service worker |
| Preferences persist and survive a reload | pass |
| Reminder cron | `notified 1, webPushed 1`, notification shown |
| Event reminders off | `skipped 1, webPushed 0`, nothing shown |
| Switch off | subscription row deleted |

## The bucket is fixed (later the same day)

The owner granted SSH explicitly, so `deploy/spaces-cors.mjs` ran on the
droplet, inside the api container where the credentials and `node_modules`
already are:

    docker compose exec -T api-1 sh -c 'cp /tmp/spaces-cors.mjs ./run.mjs && node ./run.mjs'

Verified from outside afterwards: a preflight from `https://evotv.co` answers
**200 with `access-control-allow-origin: https://evotv.co`**, `PUT` allowed,
`ETag` exposed. An origin that is not on the list still gets 403. Uploads from
the deployed dashboard work now.

Note for next time: an ESM script resolves its imports from **its own
directory**, so `/tmp/script.mjs` cannot see `/app/node_modules`. Copy it into
the app directory and run it there.

## Uploads work, and the production bucket will refuse them

Uploads had never been exercised end to end and could not be: the storage
adapter hardcoded DigitalOcean's endpoint, so a local checkout had nothing to
upload to. `SPACES_ENDPOINT` and `SPACES_FORCE_PATH_STYLE` point the same code
at any S3-compatible server, defaulting to exactly what production does.

Running it found a production blocker that reading could not have:

**`evotv-media` has no CORS rule.** The dashboard PUTs straight at the bucket,
so the bucket decides whether to allow it, and a preflight for `https://evotv.co`
comes back 403 with no `Access-Control-Allow-Origin`. Every upload from the
deployed dashboard would fail, with a failed fetch as the only symptom, while
the presign itself is correct.

    curl -i -X OPTIONS "https://evotv-media.fra1.digitaloceanspaces.com/admin-uploads/probe.png" \
      -H "Origin: https://evotv.co" -H "Access-Control-Request-Method: PUT"

`deploy/spaces-cors.mjs` fixes it in one command on the droplet. **It has not
been run**: SSH from this machine is blocked by the permission classifier.

Verified against a real S3 server: presign 200, browser PUT 200, object read
back byte for byte as `image/png`, random suffix on the key, the show poster
field filled itself, and a 1200 by 400 poster refused before anything left the
browser.

## App push cannot work yet, and it is not the missing handset

Chasing "a push has never reached a handset" found something a handset would
not have explained. Checked against Expo's own API with the robot token:

- `androidAppCredentials`: `[]`
- `iosAppCredentials`: `[]`
- no `google-services.json` anywhere in the app repo, and no
  `expo.android.googleServicesFile` in `app.json`

So a real phone would have failed to get a token, and the registration hook
swallowed every error, so it would have looked like nothing happened at all.
The swallowing was right in intent, push must never block a sign-in. The
invisibility is what cost the time. Failures are recorded in
`lib/push/state.ts` now, warned to the console, and shown in Settings under
**Push on this device**.

`EVOTV-app/docs/PUSH-SETUP.md` has the two account-holder tasks: a Firebase
project for Android and an APNs key for iOS. Neither is a code change.

## Can we embed Twitch or Kick on the live TV?

Tested rather than guessed, in real Chrome at desktop and phone widths.

| | Desktop | Phone user agent |
|---|---|---|
| Twitch (`player.twitch.tv`, `parent=`) | plays | **renders nothing at all** |
| Kick (`player.kick.com/<channel>`) | plays | plays, with "Visit KICK for HD" over it |

Twitch's embed being blank on a mobile user agent is close to disqualifying on
its own: most of this audience is on a phone. Kick's works, but the player
carries Kick's logo, a follow affordance and a call to action pointing at Kick
for the better quality, inside our own page.

Neither hands over an HLS URL, so neither existing player can use one. The app
would need `react-native-webview`, which is not a dependency today, plus a
second player path. Chat, polls, tips, the ad slot, viewer counts and the watch
data all come from our own player and all of them go.

The standing decision in `DECISION-live-streaming.md` holds: Cloudflare Stream.
Where a partner streams on Twitch or Kick, ask them to multistream to our RTMP
ingest rather than embedding them, which keeps the viewer, the data and the
monetisation on EVO TV. Linking out to a partner's channel is fine; putting
their frame inside the live TV surface is not.

## The app, later the same day

**The tab bar was not a design problem.** `pnpm apk` copies the repo to
`C:\Users\Sweez\evo` with `robocopy /E`, which only ever adds, so
`app/(public)/api-access` - deleted in June - was still in the copy and still
in every APK. Expo Router turns each of its four routes into a tab, which is
the ten-item bar with unreadable labels. `/PURGE` fixes it, and the
route-count guard added alongside immediately caught a second one: `/XD
android` matched **every** directory called android at any depth, so
`app/(public)/apps/android` has never been in an APK at all.

**Nothing built by that script can be trusted to match the repo**, including
the 15 August APK. Rebuild before reading anything from a device.

**The splash is the owner's pick, F, emerge**: the mark arrives overbright and
slightly large and sharpens as the glow falls back. The glow is a baked PNG
because RN has no CSS filters and no radial gradients. The tracked-out `EVO TV`
caption under the logo is gone; the mark says it and "Powered by EVO TV" is on
the same screen.

**The lock screen was asking the same question twice.** It gated on "is there a
session?", which is also true one tick after somebody types their password, so
a normal sign-in landed on "EVO TV is locked". The unlock exists so a session
already on the phone opens with a thumb *instead of* a password. Only a session
restored at startup locks now.

## Kick and Twitch, the follow-up question

Asked whether we could stream to Kick or Twitch and show that as the main TV,
to spend nothing on delivery. Tested rather than argued:

- **Twitch's embed renders nothing on a mobile user agent.** Most of this
  audience is on a phone.
- **Kick's embed works on a phone**, and carries Kick's logo and a "Visit KICK
  for HD" call to action over our own page.
- **Kick's API answers 403 to a cross-origin fetch**, even from a real browser,
  so there is no playback URL to pull into our own player. The iframe is the
  only route, which means a WebView in the app and a second player path.

So it is possible, and it costs the product: chat, polls, tips, the ad slot,
viewer counts and watch data all come from our own player. Cloudflare Stream
delivers from the edge for about a dollar per thousand minutes, so the droplet
was never going to serve the video anyway. The answer is to multistream: our
own ingest for the player, Kick or Twitch alongside it for reach.
