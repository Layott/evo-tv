## 2. The password change on the website was fake

The form waited 700ms and said "Password changed". Nothing was sent anywhere
and the old password kept working. Somebody rotating a compromised password
would have believed they were safe and would not have been.

It now posts to Better-Auth's `change-password` with `revokeOtherSessions`.
Verified against a local account, which is the only way this could be proved:
wrong current password gave "Invalid password" and no change; the correct one
changed it; signing in over the API afterwards answered **401 for the old
password and 200 for the new one**.

Error text also comes out of the response body now rather than being invented,
so the toast says "Invalid password" instead of
`{"code":"INVALID_PASSWORD","message":"Invalid password"}`.

## 3. Releases now come from EAS, and the website gets that same artifact

Owner's rule: the APK on EAS and the APK on evotv.co are one file, not two
builds of one commit.

`pnpm release:android` does the whole thing: `eas build`, wait, download the
artifact, rename it from the version, build number and commit **EAS** recorded,
publish that file to the website, then `eas update` on the same channel. The EAS
build id and artifact URL go into the release row's notes.

Four things had to be sorted out before the first build would run:

- **No EAS session on this machine, ever.** `eas login` needs a TTY and the
  tooling has none. A robot token in the gitignored `.publish.env` covers it,
  and `release-android.mjs` reads that file itself.
- **The build counters disagree.** The local script numbers builds by commit
  count and reached 229; EAS keeps its own, starting at 1. The site serves the
  highest build number, and Android refuses a lower versionCode over an
  installed copy. Set once to 230 through the GraphQL API, because
  `eas build:version:set` is interactive-only in the pinned CLI. `autoIncrement`
  now carries it forward, and the first cloud build took 231.
- **`autoIncrement` was only on the production profile**, so every preview build
  would have carried the same versionCode as the last.
- **Signing.** With no credentials configured, EAS generates a keystore. A new
  key is worse than a failure: the APK builds, and every phone with 229 on it
  refuses the update as "app not installed" with nothing to explain why.
  `credentialsSource: local` plus a gitignored `credentials.json` points at the
  same `evotv-release.keystore` the local script uses. Fingerprint is recorded
  in `EVOTV-app/docs/RELEASE-android.md`.

`pnpm apk` still exists, and its header now says it is not a release.

## 5. Landmines found today

- **`eas login` and `eas build:version:set` both need a TTY.** Piping input does
  not satisfy the prompt library. The GraphQL API is the way round it, and the
  same trick was needed for FCM credentials in August.
- **A stale `.next` breaks `tsc`.** `pnpm typecheck` failed with four syntax
  errors inside `.next/dev/types`, nothing to do with the source. `rm -rf .next`
  and it passes.
- **The integration tests skip themselves.** 21 of 22 skip without `REDIS_URL`,
  and vitest reports that as a pass. Run a broker first:
  `docker run --rm -d -p 6399:6379 --name evo-test-valkey valkey/valkey:8-alpine`,
  then `REDIS_URL=redis://127.0.0.1:6399 pnpm test:integration`. Nine pass.
- **Local development needs Docker running.** Postgres for dev is
  `deploy/docker-compose.dev.yml` on port 55432; without it every auth call
  fails with `ECONNREFUSED` and the UI says only "Sign up failed".

**Encoder setup page**, at Streams, Encoder setup. OBS, vMix and ffplayout with

will not load on OBS 32, Aitum honours resolution and ignores bitrate and
keyframe, `NV_ENC_ERR_INCOMPATIBLE_CLIENT_KEY` means a driver installed but not
rebooted into, and the bandwidth in the playlist comes from the server config
rather than the stream, so an encoder that overshoots makes the playlist promise
what it cannot keep. None of that was written anywhere an operator would look.

**A page for when a deploy is in flight.** `deploy.sh` restarts one container at
a time and waits for health, so the other usually keeps serving. Usually is not
always: a migration or a slow build leaves a window where nothing answers and
every button fails with no explanation. Caddy serves a standalone page on 502,
503 and 504 that says what is happening and polls health rather than reloading
blindly, because a reload every few seconds during a deploy is a request storm
against a server that is already busy.

That page then shipped broken, and the fix is the landmine worth keeping:
**`deploy.sh` syncs a fixed list of files**, `maintenance.html` was not on it,
so the config pointing at `/srv/maintenance` went live while the file it points
at did not exist. A visitor would have got Caddy's own error page, which is the
exact thing this replaced. The compose file also gained a bind mount, and **a
Caddy reload cannot pick up a mount**, so the container is recreated when the
compose file itself changes. Same trap as the one already at the top of that
loop: a change to which files get synced is invisible until the script doing the
syncing is itself synced.

**The audit log in English.** A row said `delete` on `ad ad_a0c8b70c397eeff5`,
so answering "which ad" meant copying an id into another screen. Names are

with no name behind it still shows as an id, which is honest about a deleted

### The three chat errors were four bugs

Pin, delete and ban each answered with a red toast, and the room only ever
showed the moderator's own lines.

- **Pin and delete were called with the wrong arguments.** The client takes
  `(streamId, messageId)`; the chat passed `(messageId, handle)`. Both strings,
  so it compiled, and the request went to
  `/api/streams/<messageId>/chat/<handle>/pin`, a 404. Both take a named object
  now, so the arguments cannot be swapped again. **This is the third time in
  two days that a same-typed argument or wrapper has produced a silent
  failure**, after `{ message }` and `adminUpdateStream`.
- **Ban went to the wrong endpoint entirely**, posting `{ action: "ban" }` at
  the partner channel route with a stream id in the channel's place. That route
  has no ban action, only `timeout`, which emits an event and persists nothing,
  so a banned viewer was back on reload. There is a real route beside pin and
  delete now: it writes the same `chat_banned` sanction the moderation queue
  writes, deletes the message, and refuses to ban yourself, a head admin or an
  equal-ranked admin.
- **Nobody else's messages arrived.** The bus publishes
  `{ type: "message", message }` and the page cast that envelope to a message,
  so `id` and `body` were undefined and every frame was dropped, `deleted` and
  `pinned` included. A room with two people looked like a room with one. The app
  had the contract right all along, which is why only the website was affected.
- **`role !== "admin"`** guarded pin and delete, false for a head admin and for
  the moderators the buttons exist for.

Proved on production: pin gave "Message pinned", delete gave "Message deleted",
ban on an admin gave "Cannot ban an admin" (the rank guard, with the server's
own words in the toast). The test message was deleted and the pin undone.

### Every CMS upload was private

The broken thumbnail on /admin/streams was not a rendering bug: the object
answered `AccessDenied` on the CDN **and** on the origin. The presigned PUT asks
for `public-read` in its hoisted query string and the bucket does not apply it
that way, so everything the dashboard has ever uploaded landed unreadable. The
upload succeeded, the URL was saved, and the only symptom appeared on a screen
nobody would connect to an upload.

- `makePublic()` sets the ACL server-side, where it is a header, then **fetches
  the file over its public URL**. An ACL call returning 200 is not evidence the
  file can be read, and trusting that kind of evidence is the whole bug.
- The upload field calls it before handing the URL to the form and fails the
  upload if the file is unreadable, so a broken URL cannot reach a row.
- Settings gained an **Uploads** tab that repairs what is already there, capped
  at 300 files a run. Run on production: 8 checked, 2 unreadable, 2 repaired,
  and the thumbnail now returns 200.
- `image/gif` was in the picker's accepted list and missing from the presign's,
  so an animated ad creative was accepted by the file dialog and refused with a
  415.

### Downtime ads could not be uploaded at all

Preroll, channel break and dropped-feed filler are rendered in a `<video>` tag
and the ads form only ever offered an image picker, so an uploaded JPEG failed
to load, the error handler ended the break, and the viewer was dropped back onto
the feed that was not there. The player skipped non-video creatives silently.

The creative picker follows the placement now, and saving is blocked with an
explanation when the two do not match, which is the state you get by switching
placement after uploading. `looksLikeVideo` is one shared definition.

### Analytics answers a date now
