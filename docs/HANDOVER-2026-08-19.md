## 2. The password change on the website was fake

The form waited 700ms and said "Password changed". Nothing was sent anywhere
and the old password kept working. Somebody rotating a compromised password
would have believed they were safe and would not have been.

It now posts to Better-Auth's `change-password` with `revokeOtherSessions`.
Verified against a local account, which is the only way this could be proved:
wrong current password gave "Invalid password" and no change; the correct one
changed it; signing in over the API afterwards answered **401 for the old
password and 200 for the new one**.

Error text also comes out of the response body now rather than being invented,
so the toast says "Invalid password" instead of
`{"code":"INVALID_PASSWORD","message":"Invalid password"}`.

## 3. Releases now come from EAS, and the website gets that same artifact

Owner's rule: the APK on EAS and the APK on evotv.co are one file, not two
builds of one commit.

`pnpm release:android` does the whole thing: `eas build`, wait, download the
artifact, rename it from the version, build number and commit **EAS** recorded,
publish that file to the website, then `eas update` on the same channel. The EAS
build id and artifact URL go into the release row's notes.

Four things had to be sorted out before the first build would run:

- **No EAS session on this machine, ever.** `eas login` needs a TTY and the
  tooling has none. A robot token in the gitignored `.publish.env` covers it,
  and `release-android.mjs` reads that file itself.
- **The build counters disagree.** The local script numbers builds by commit
  count and reached 229; EAS keeps its own, starting at 1. The site serves the
  highest build number, and Android refuses a lower versionCode over an
  installed copy. Set once to 230 through the GraphQL API, because
  `eas build:version:set` is interactive-only in the pinned CLI. `autoIncrement`
  now carries it forward, and the first cloud build took 231.
- **`autoIncrement` was only on the production profile**, so every preview build
  would have carried the same versionCode as the last.
- **Signing.** With no credentials configured, EAS generates a keystore. A new
  key is worse than a failure: the APK builds, and every phone with 229 on it
  refuses the update as "app not installed" with nothing to explain why.
  `credentialsSource: local` plus a gitignored `credentials.json` points at the
  same `evotv-release.keystore` the local script uses. Fingerprint is recorded
  in `EVOTV-app/docs/RELEASE-android.md`.

`pnpm apk` still exists, and its header now says it is not a release.

## 5. Landmines found today

- **`eas login` and `eas build:version:set` both need a TTY.** Piping input does
  not satisfy the prompt library. The GraphQL API is the way round it, and the
  same trick was needed for FCM credentials in August.
- **A stale `.next` breaks `tsc`.** `pnpm typecheck` failed with four syntax
  errors inside `.next/dev/types`, nothing to do with the source. `rm -rf .next`
  and it passes.
- **The integration tests skip themselves.** 21 of 22 skip without `REDIS_URL`,
  and vitest reports that as a pass. Run a broker first:
  `docker run --rm -d -p 6399:6379 --name evo-test-valkey valkey/valkey:8-alpine`,
  then `REDIS_URL=redis://127.0.0.1:6399 pnpm test:integration`. Nine pass.
- **Local development needs Docker running.** Postgres for dev is
  `deploy/docker-compose.dev.yml` on port 55432; without it every auth call
  fails with `ECONNREFUSED` and the UI says only "Sign up failed".

## 7. Afternoon: rooms, the audit log, and the first of the owner's list

good at one. Rank still decides seniority; a capability decides who opens which
