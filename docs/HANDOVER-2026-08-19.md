## 2. The password change on the website was fake

The form waited 700ms and said "Password changed". Nothing was sent anywhere
and the old password kept working. Somebody rotating a compromised password
would have believed they were safe and would not have been.

It now posts to Better-Auth's `change-password` with `revokeOtherSessions`.
Verified against a local account, which is the only way this could be proved:
wrong current password gave "Invalid password" and no change; the correct one
changed it; signing in over the API afterwards answered **401 for the old
password and 200 for the new one**.

Error text also comes out of the response body now rather than being invented,
so the toast says "Invalid password" instead of
`{"code":"INVALID_PASSWORD","message":"Invalid password"}`.

## 3. Releases now come from EAS, and the website gets that same artifact

Owner's rule: the APK on EAS and the APK on evotv.co are one file, not two
builds of one commit.

`pnpm release:android` does the whole thing: `eas build`, wait, download the
artifact, rename it from the version, build number and commit **EAS** recorded,
publish that file to the website, then `eas update` on the same channel. The EAS
build id and artifact URL go into the release row's notes.

Four things had to be sorted out before the first build would run:

- **No EAS session on this machine, ever.** `eas login` needs a TTY and the
  tooling has none. A robot token in the gitignored `.publish.env` covers it,
  and `release-android.mjs` reads that file itself.
- **The build counters disagree.** The local script numbers builds by commit
  count and reached 229; EAS keeps its own, starting at 1. The site serves the
  highest build number, and Android refuses a lower versionCode over an
  installed copy. Set once to 230 through the GraphQL API, because
  `eas build:version:set` is interactive-only in the pinned CLI. `autoIncrement`
  now carries it forward, and the first cloud build took 231.
- **`autoIncrement` was only on the production profile**, so every preview build
  would have carried the same versionCode as the last.
- **Signing.** With no credentials configured, EAS generates a keystore. A new
  key is worse than a failure: the APK builds, and every phone with 229 on it
  refuses the update as "app not installed" with nothing to explain why.
  `credentialsSource: local` plus a gitignored `credentials.json` points at the
  same `evotv-release.keystore` the local script uses. Fingerprint is recorded
  in `EVOTV-app/docs/RELEASE-android.md`.

`pnpm apk` still exists, and its header now says it is not a release.

### The three chat errors were four bugs

Pin, delete and ban each answered with a red toast, and the room only ever
showed the moderator's own lines.

- **Pin and delete were called with the wrong arguments.** The client takes
  `(streamId, messageId)`; the chat passed `(messageId, handle)`. Both strings,
  so it compiled, and the request went to
  `/api/streams/<messageId>/chat/<handle>/pin`, a 404. Both take a named object
  now, so the arguments cannot be swapped again. **This is the third time in
  two days that a same-typed argument or wrapper has produced a silent
  failure**, after `{ message }` and `adminUpdateStream`.
- **Ban went to the wrong endpoint entirely**, posting `{ action: "ban" }` at
  the partner channel route with a stream id in the channel's place. That route
  has no ban action, only `timeout`, which emits an event and persists nothing,
  so a banned viewer was back on reload. There is a real route beside pin and
  delete now: it writes the same `chat_banned` sanction the moderation queue
  writes, deletes the message, and refuses to ban yourself, a head admin or an
  equal-ranked admin.
- **Nobody else's messages arrived.** The bus publishes
  `{ type: "message", message }` and the page cast that envelope to a message,
  so `id` and `body` were undefined and every frame was dropped, `deleted` and
  `pinned` included. A room with two people looked like a room with one. The app
  had the contract right all along, which is why only the website was affected.
- **`role !== "admin"`** guarded pin and delete, false for a head admin and for
  the moderators the buttons exist for.

Proved on production: pin gave "Message pinned", delete gave "Message deleted",

## 11. Late night: why the filler never played, in four parts

Owner report: "the filler still does not load when nothing is showing", plus
"it did not pick up when I restarted the stream until I refreshed", plus "the
home page video should play by itself".

Each of these had its own cause, and each one hid the next.

1. **The filler was mounted on one page.** `ChannelBreaks` was in the home hero
   and nowhere else, so `/stream/<id>`, where Watch now sends everyone, had no
   filler, no breaks and no on-air card.
2. **It was gated behind the Channel breaks master switch**, which is off.
   Covering an outage is not advertising on a schedule.
3. **The filler ad row had no creative.** The row being served had an empty
   `mediaUrl`: saved without a file, accepted by the form, handed out by the
   serve endpoint, which also stopped the working row from ever being picked.
   Save is now disabled without a creative, both write endpoints reject an
   empty one, and serving skips rows that cannot render.
4. **A dead feed does not raise an error.** This is the one that mattered most.
   nginx keeps a five minute playlist, so stopping the encoder leaves the
   manifest 200 and the player simply runs out of segments: no `error`, no
   `ended`, often no `stalled`. Later, once nginx cleans up, the manifest 404s
   and hls.js retries the network error forever, leaving `readyState` 0 with no
   data and `paused` true, which reads exactly like a viewer who pressed pause.

   The detector now asks the only honest question, whether the picture is
   moving, and treats **twelve seconds of a still clock** as a dead feed. A
   viewer's pause always has data behind it; nothing buffered and nothing
   decoded is a feed that never arrived. Recovery is the same test in reverse,
   because a stalled element keeps a healthy `readyState`.

   This is also the only signal available inside the reconnect window: with
   "Wait an hour" set, the broadcast stays marked live on purpose, so nothing
   off-air renders and no server event fires.

**Proved on production** at 00:2x with every playlist 404ing: both the home hero
and the watch page play `evo-tv-ad-5290081c19b65974.mp4` on a loop, labelled
"Back shortly", with the ad's own click-through. Two video elements on the page,
the live one holding nothing and the filler playing.

Also fixed on the way:

- **The watch page never updated.** It read the stream once and never again, so
  starting the encoder changed nothing on an open tab. It now listens to
  `/api/sse/channel`, which the hero has used since it was built, with a thirty
  second poll as the floor.
- **Autoplay needed a click.** It depended on a chain of hls.js events; a
  watchdog now checks whether the element is actually playing and starts it
  muted if not, and stands down the moment the viewer pauses.

**A deploy used to break an open tab, and no longer does.** Chrome logged
`ChunkLoadError: Failed to load chunk ...` eighteen times against chunk names
from the previous build: every build renames the chunks and the old names stop
existing the moment it is live, so a tab loaded beforehand loses whatever it
lazily imports next, with no visible error and no way back but a manual reload.

`components/providers/stale-build-guard.tsx` catches it on `window` and in the
error boundary, and reloads once, at most once a minute per tab, because a
reload loop against a genuinely broken build is worse than the fault. Proved on
production: a dispatched `ChunkLoadError` reloaded the page and cleared a marker
variable, and a second one inside the minute did not.

## 13. Into 20 August: the player heals itself, and polls become an event

### The filler would not leave when the broadcast came back

Reported twice, and both reports were right. `startLoad()` is the correct answer
to a dropped segment and the wrong one to a **deleted manifest**: nginx removes
the playlists a while after the encoder stops, every request 404s, hls.js
exhausts its manifest retries and stops asking. The feed returns and nothing
asks for it again, so the viewer watches filler over a channel that is on air
until they reload, which is exactly what the owner had to do.

A live player holding no data now re-requests its source **every eight seconds**
for as long as that stays true. The filler's own recovery check then sees data
arrive and stands down. One request per eight seconds during an outage is the
whole cost.

### Polls, migration 0049

A poll had a question, options and a clock, so it could only ever be a quick
sidebar vote. It now carries four decisions, made per poll:

| | |
|---|---|
| Who can vote | anyone with an account, or subscribers only |
| Results while it runs | shown, or withheld until it closes |
| Winner on screen | takes the picture for a few seconds at the close |
| Change your mind | allowed, or one vote decided the first time |

Two things worth keeping:

- **A hidden result is hidden on the server.** Sending the counts and asking the
  screen not to draw them puts the answer in the network tab of anybody curious,
  and the reason to hide them is that nobody has them yet. Staff get the real
  numbers, because running the poll is the job.
- **`role !== "admin"` guarded poll creation**, so a head_admin could not start
  one. That is the fourth instance of that comparison in two days.

Still to come on polls: the live metrics panel for admins, and the winner
