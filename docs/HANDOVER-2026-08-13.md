### 3-hour idle logout on the website (owner request)

Browsers are signed out after three quiet hours. The app is deliberately
exempt: it keeps the week-long session and will lock behind fingerprint or face
instead, because killing a phone session every three hours only means retyping
a password, while a shared cybercafe machine is the actual risk.

| File | What |
|---|---|
| `lib/auth/idle.ts` | New. Owns the window, the cookie parse, and the revoke. |
| `lib/auth/index.ts` | `expiresIn`/`updateAge`/`cookieCache` now come from that module. `updateAge` dropped from 24h to 5min, which is what makes the idle clock tick. |
| `lib/auth/guards.ts` | `getSession()` revokes before Better-Auth reads. |
| `app/api/auth/[...all]/route.ts` | Same check on the route the browser's `useSession()` hits, plus the `evotv_signed_out=idle` crumb. |
| `app/(auth)/login/page.tsx` | Says why you were signed out. **Also removed the "Remember me for 30 days" checkbox**, which was wired to nothing and promised the opposite of the new rule. |

**The one trap here:** the check must run *before* Better-Auth reads the
session, because reading it slides the expiry forward. A check made on the
session Better-Auth hands back is looking at a timestamp it just refreshed and
would never fire.

Proven end to end against a real sign-up on a local server:

- The session cookie really is `<token>.<signature>`, so splitting on the first
  dot recovers the token. Confirmed against the token in the sign-up response.
- Aged to 2 hours idle: still signed in.
- Aged to 4 hours: response body `null`, all three session cookies cleared,
  `evotv_signed_out=idle` set, and the row gone from the database.
- `tsc --noEmit` and `pnpm build` clean.

The test user and the throwaway script that aged it have both been deleted.

## 3. Findings that change what the next session should believe

### The native hero is not broken, the CORS wall is

`docs/HANDOVER-NATIVE-2026-08-12.md` says to run the app and check the hero,
and treats an empty hero as a client bug. It is not. **Prod refuses
`http://localhost:8081` outright** - no `Access-Control-Allow-Origin` header at
all - so every request the app makes from a dev machine fails, and the hero
renders nothing because `channel` is undefined, exactly as written.

`curl https://api.evotv.co/api/channel/main` returns a real channel with a
populated `onNow`, so the data is fine and the endpoint is fine.

To actually see the hero, point the app at a local backend
(`EXPO_PUBLIC_API_BASE_URL=http://localhost:3060`) and give that database a
main channel. Do **not** add localhost to the prod origin list.

### The local database is the old Neon one, and it has no main channel

`backend/.env.local` still carries Vercel-era Neon credentials. It connects and
it has the EPG (`onNow`/`upNext` come back populated), but
`/api/channel/main` returns `channel: null` because no stream there is flagged
`isMainChannel`. Prod (DigitalOcean) does have one. Anything read locally is
the old copy, so do not treat local counts as production truth.

### Fingerprint / face unlock in the app (owner request)

The other half of the idle sign-out. New files: `lib/security/app-lock.ts`,
`components/providers/app-lock-gate.tsx`, `components/settings/app-lock-row.tsx`,
plus `expo-local-authentication` and its Face ID plugin entry in `app.json`.

- Not a second factor. The session is already valid; this only decides whether
  the person holding the phone sees it.
- Not a lockout. The device passcode fallback is left on and the lock screen
  carries a sign-out, so a failed scan cannot strand anybody.
- Re-locks after a minute in the background, not instantly, or a glance at a
  notification throws a viewer out of a stream. Only a real `background` starts
  that clock: iOS reports `inactive` when a system dialog opens, **including
  the unlock prompt itself**, so counting that would re-lock the app the instant
  it was unlocked.
- **Unverified on a device.** Typecheck only.

### Three app fixes carried over from 12 August

- **`requiresAuth`.** A signed-out viewer opening a stream got an empty player
  stuck at 0:00, because the app never read the flag the API sends when it
  withholds the manifest URL. Now shows the same sign-in panel the web does.
  Reproduced and fixed against a local backend.
- **Onboarding was device-local**, so the same account onboarded again on every
  new handset. `PATCH /api/users/me` now takes `onboarded: true` and coalesces
  the stamp; the app asks the account as well as the device on hydration.
  Verified null → stamped → same stamp on a repeat call.
- **The main-channel hero works.** See section 3.

### A trap that cost twenty minutes

`EVOTV-app/node_modules` was still linked to the repo's **old** path from
before the move into `EVOTV-PLATFORM`, and that directory no longer exists.
Reads worked because the linker is `hoisted`, so the files are real, but any
`pnpm add` failed with `ERR_PNPM_UNEXPECTED_VIRTUAL_STORE`. Fixed by
`CI=true pnpm install` (the `CI` var is needed, or pnpm asks for a TTY
confirmation to purge and aborts). Kill the Metro server first; it holds locks.
